# Native preview colour and lazy build tools

The photographic 3.0.1 benchmark found higher build overhead than vite-imagetools and no established full-preview gain from accelerating only the BlurHash projection. Profiled raster builds also loaded SVGO's modules even though no SVG output was requested. Preview colour asked Sharp for channel statistics, entropy and sharpness despite consuming only the dominant colour.

Version 3.1 computes the 4096-bin RGB histogram in the existing Rust/WASM module for all build preview strategies (LQIP, color, BlurHash and ThumbHash). The independently implemented integer quantization matches the installed libvips histogram's `floor(channel * 16 / 257)` behavior. Alpha is ignored, matching Sharp's colour calculation. A unique maximum produces the same midpoint RGB value; tied maxima defer to Sharp so its tie-breaking is preserved. A seeded, alpha-aware compatibility test checks results against Sharp, and paired photographic runs require complete preview JSON identity against the published 3.0.1 package.

The new export consumes at most 32×32 RGBA pixels and a fixed 4096-element u16 histogram. Counts cannot exceed 1024. The precompiled module grows from 1719 to 2081 bytes while retaining a fixed, non-growable 64 KiB memory, no imports and no allocator. The synchronous host validates dimensions before memory writes. Preview decoding overlaps module initialization; `placeholder=none` does not initialize it. The module stays on Node/build paths. Consumer projects need neither Rust nor generated declarations.

The improvement removes unnecessary work; it is not all attributable to the language. A separate optimized-JavaScript histogram control uses the same quantization, tie handling and colour-string output. Initialization, first batches and steady-state costs are measured separately. The deployment decision retains Rust's fixed memory boundary and existing reproducible build path; a universal Rust performance advantage is not assumed.

Ambiguous colour maxima fall back to Sharp statistics. The bundled WASM itself is an installation requirement for previews: a missing file or incompatible ABI fails preview processing rather than silently changing output. Restore the package artifact by reinstalling; contributors can rebuild with the pinned toolchain. `placeholder=none` does not read the artifact. Package checks verify that the published archive includes it, and a fresh packed consumer exercises the installed kernel.

SVGO is imported only when SVG output is actually requested. Default policy creation becomes a pure factory while retaining all existing deep freezes, so component-only browser bundles can discard unused server policy initialization. Image/Picture semantics, codec settings, HTTP request admission and worker termination deadlines remain unchanged.

Warm builds reuse validated preview metadata in a separate `node_modules/.cache/svelte-imageway-previews` disk cache (8 MB) and per-plugin immutable memory cache (4 MB, at most 4096 values). Each JSON entry is limited to 32 KiB before parsing; the underlying disk reader refuses files over the entire 8 MB budget before reading. Content digest, pipeline revision, codec versions, strategy and byte/pixel/deadline policies form the key. Source admission and metadata validation still happen first. Invalid entries are deleted and regenerated, and `none` does no preview-cache IO. Keeping this directory alongside, rather than inside, the variant cache preserves its independent eviction policy. This avoids repeated decodes, not just repeated histogram calculations.

Components remove a redundant derived value and reuse the chosen image representation without copying the artifact. These small changes preserve provider selection, attributes, preload, snippets, events and reduced-motion behavior. Bundle budgets remain a separate measured gate; this does not establish the old 1.5 KiB target.

Other short JS paths (directive parsing, bounded width deduplication, format decisions and srcset assembly) are not moved across the WASM boundary without a demonstrated whole-build gain. Content hashing already uses Node's native crypto implementation. The dominant-colour control evaluates an actual CPU loop with host-copy overhead included. Sharp/libvips remains responsible for decode/resize/encode: default AVIF encoding dominates the larger cold workload, so a Rust orchestration rewrite without a measured encoder gain is not justified here.

Compare against the SHA-256-pinned npm 3.0.1 tarball, using the same 24 Kodak photos in alternating fresh Node processes. Measure responsive builds without previews, responsive builds with LQIP, ordinary default imports, complete previews, optimized JS/Rust histogram controls and real Svelte client bundles. Check encoded image bytes and complete preview JSON rather than comparing filenames (pipeline revisions legitimately change URL identities). Keep previous benchmark data dated and immutable.

Reference behavior: [Sharp statistics](https://github.com/lovell/sharp/blob/main/src/stats.cc), [libvips n-dimensional histogram](https://github.com/libvips/libvips/blob/master/libvips/arithmetic/hist_find_ndim.c). These sources describe compatibility behavior; the Rust implementation is independently written and verified against the installed native library.
